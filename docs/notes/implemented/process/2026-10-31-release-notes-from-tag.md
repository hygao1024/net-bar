# Agent Note: Release notes from annotated tags

Status: implemented

## Problem

v1.2.0 的人工版本说明写入了附注标签，但发布工作流使用自动生成说明，仅生成完整变更链接，没有将原文带到发布页面。

## Decision

GitHub Release 正文直接使用附注标签说明，由 `--notes-from-tag` 读取。工作流获取完整历史和标签，并在构建前验证标签存在、对象类型为附注标签、说明非空白；轻量标签不允许回退为提交消息。首次发布的版本说明以发布标签为准，具体操作由[发布文档](../../../releases.md#github-发布)维护。

检出显式使用短标签名称，避免 checkout 在标签事件中以提交 SHA 覆盖运行器内的附注标签引用；构建前另行核对 HEAD 与标签提交一致。创建草稿前失败时，手动入口允许主分支工作流按原标签重新运行，使工作流修复不需要移动发布标签。手动入口只改变工作流来源，产品源码仍由既有标签拥有。

通过专用创建脚本固定使用 `--cleanup=verbatim`，保留 Markdown 标题和换行；Git 默认的注释清理会删除以 `#` 开头的标题。仅修正文档命令仍依赖操作者记住参数，因此创建入口读回标签与确认稿比对，并拒绝空白或无效确认稿；已有标签不覆盖。临时仓库检查运行真实入口，并植入标题已被清理的标签证明原稿比对会拒绝格式丢失，工作流在构建前运行该回归检查。

## Alternatives considered

- 继续使用自动生成说明：不能保证人工撰写的说明被发布，缺少合并请求时尤其可能只剩链接。
- 在仓库额外维护每个版本的说明文件：当前发布已使用附注标签，增加第二份持久事实容易不一致；创建标签时可从临时 Markdown 文件读取。

## Consequences

后续发布必须使用附注标签，说明的内容准确性仍需人工核对，非空检查不判断文字质量。此流程不修改已有公开版本的标签或附件。已公开版本的正文可按用户确认稿单独修订并读回核对；网页拥有修订后的说明，原标签保留历史文本，不为修正文案改写版本身份。

本地检查通过真实临时 Git 仓库覆盖有效多行中文说明，以及轻量、空白和缺失标签的拒绝路径。v1.3.0 首次线上运行暴露了 checkout 用提交 SHA 替换本地标签的行为，远端附注标签没有改变；发布前检查成功阻止该检出状态继续执行。
