# 选择变更检查

目标是用最小成本获得能捕获本次回归的证据，而不是机械运行所有命令。

## 确认范围

1. 读取适用的 `AGENTS.md`、项目清单、任务脚本和原生 hook 配置；这些来源共同说明仓库真正拥有的检查，不另建命令映射。
2. 检查当前分支和工作区状态。
3. 确认 live base（实时基线）和 head（目标提交），使用仓库已有的 `change-scope` 或等价入口检查完整范围；没有专用入口时，基于已验证引用分别检查 committed、staged、unstaged 和 untracked 路径，并说明范围限制。
4. 将 committed、staged、unstaged 和 untracked 路径映射到入口、消费者、外部行为和交付物；不要只按扩展名选测试。

`change-scope` 不猜测或获取 base，不查询 hosting provider（代码托管服务），也不选择测试。base retarget（重新指定）或合并新基线后重新生成报告。

## 选择证据

先从真实改动映射到受影响行为，再选择仓库已有的最窄命令。命令名称只能帮助发现入口，不能证明它覆盖了该行为。

- 局部逻辑：直接覆盖该行为的测试。
- 共享接口：提供方、消费者和类型证据。
- UI、CLI（命令行界面）、协议或模型可见输出：非平凡变化必须通过真实可运行组合验证；目标仓库已有 keyless snapshot（无凭据快照）能力时更新或扩展它，否则使用真实入口 smoke test 并记录原因与残余风险。单元测试或 mock-only 测试不能单独作为证据。
- 持久化、协议和迁移：旧输入、新输出、无效输入和恢复路径。
- 权限、安全和路径：允许、拒绝及替代入口。
- 构建、exports（导出）、依赖和发布文件：真实构建、产物检查和启动测试。
- 文档与 Agent Notes：仓库已有的文档和工作流检查。

如果仓库缺少本次风险所需的检查，把补足行为证据纳入同一变更；不要仅为登记命令增加新的通用 schema（模式）或 runner。

只有改动真正跨越多个领域、正在诊断完整流水线，或用户明确要求时，才运行所有检查。不要仅因随后 commit 或 push 而手动重复未受后续修改影响的通过结果。

## 处理结果

- 失败时先确认改动是否触达失败路径，再决定修复范围。
- 环境问题必须有具体命令、错误和平台证据。
- 缺少凭据或目标平台时，运行仍有效的无凭据检查并说明残余风险。
- 报告实际运行的命令；pending（等待中）、skipped（跳过）和未运行不能描述为通过。
