# 发现可证明的简化

目标是删除、合并、降级或私有化真实表面，而不是追求文件数、建议数或代码行数。审计与 Review 请求默认只读；只有明确要求修复、重构或实施时才修改仓库。

## 建立范围

确认真实 diff 或用户指定 scope、适用的 `AGENTS.md`、架构文档、Agent Notes、入口和动态装配方式。先理解已有决定；记录过的结构不是不可改变，但新证据必须能够胜过其理由。

## 证明候选

对每个符号、配置、脚本、抽象、格式或测试资产区分：

- production consumer（生产消费者）：运行时代码、真实入口、配置加载、插件装配、生成或发布路径。
- non-production consumer（非生产消费者）：测试、文档、注释、Note 和派生产物；它们不能单独证明生产需要。
- ambiguous consumer（不明确消费者）：示例、脚本、反射、事件名、配置键和动态加载；先读取入口再分类。

强候选通常具有至少一项证据：没有生产消费者；两个可编辑表示拥有同一事实；公共 API 只服务一个内部调用方；配置或兼容分支没有当前需求和删除条件；抽象增加的概念多于消除的重复；测试只保护已无消费者的行为；成熟 builtin（内建能力）或依赖能够净删除实现、专用测试和文档。

## 判断收益和代价

- 沿调用方和替代入口确认删除不会绕过动态消费者、持久化数据、wire format（线协议格式）或公开兼容承诺。
- 比较删除后的概念、接口、状态和恢复路径，而不只比较 LOC（代码行数）。行为略有变化时，必须说明失去的能力为何可以接受。
- 引入依赖只有在维护状态、供应链代价、边界语义和剩余胶水代码都可接受，且形成 net deletion（净删除）时才算简化。
- 若候选只因“看起来复杂”、工具报 unused（未使用）或测试难写而成立，降级为待调查，不输出确定建议。
- 不为数量制造候选；一个有完整消费者证据的删除优于多条风格意见。
- 用户要求广度时先划分主要生产领域并完成代表性覆盖，优先审计所有权、重复状态和恢复机制；不能因发现第一个可靠候选就结束全局调查。

## 交付

审计时按价值和风险排序，给出位置、消费者证据、拟删除表面、失去能力、兼容风险和验证入口。实施时删除已经失去用途的实现、测试、文档、配置和 Note 投影，不保留无消费者的兼容壳。

跨边界或长期简化新增或更新 `simplification` Agent Note；局部机械删除可以豁免。完成后运行受影响行为的 focused test（聚焦测试）、真实入口或构建检查，并确认精确符号、配置键和文档引用不再残留。
