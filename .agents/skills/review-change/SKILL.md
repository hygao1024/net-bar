# 评审变更

这是评审指导，不是完整 checklist（检查清单）；目标是发现会影响合并判断的问题，而不是生成风格意见清单。

## 建立事实

1. 确认 live base（实时基线）和待评审 head（目标提交），使用仓库已有的 `change-scope` 或等价入口检查完整 diff 与工作区层；无法确认时明确范围限制。
2. 读取完整 diff、适用的 `AGENTS.md`、项目清单、相关 Agent Notes、实现两端和测试。
3. 区分本次引入的问题与原有问题；原有问题未被本次放大时不归责于当前改动。
4. 涉及异步、子进程、权限、凭据、路径或 teardown（清理）时加载 `defensive-patterns`；涉及文档、注释、诊断或用户可见文本时加载 `prose-and-docs`。

## 评审重点

- **行为与契约**：输入、输出、错误、默认值和调用方是否一致；是否静默扩大兼容范围。
- **所有权与状态**：事实来源、写入者、缓存、通知和清理责任是否明确。
- **失败与时间轴**：初始化、并发、取消、超时、重试、部分成功、重启和 teardown（清理）是否收敛。
- **安全与权限**：验证是否发生在真正执行操作的边界；是否存在绕过 schema（模式）、UI 或 wrapper（包装层）的入口。
- **范围与必要性**：新增公共 API、配置、抽象或依赖是否有当前消费者和所有者，新增概念是否删除或合并了更多表面；仅被测试或文档引用不能证明生产需要。
- **测试强度**：测试是否观察稳定外部结果，并有证据表明错误实现会失败；测试描述行为，不自动证明行为正确，过时行为应与测试一同修改。
- **交付一致性**：代码、项目配置、文档、Agent Note、迁移和用户可见产物是否描述同一现实。
- **证据选择**：实际运行的 checks 是否覆盖 diff 触达的真实行为；缺少有效检查时是否明确残余风险。
- **决策记录**：当变更触及非平凡决定时，核对是否新增或更新了真正拥有该决定的 Agent Note，并确认 Note 与已交付事实一致；取代、归档和未来价值判断由 `manage-decision-notes` 负责。
- **规则执行职责**：新增或修改的规范是否明确由仓库现有 check 或语义 Review 负责；新增 guard 是否稳定、低误报、有实质风险和可信 negative control，而不是为了让每条规则都有脚本。

自动化已经可靠阻止的问题不重复报告。格式偏好只有在降低理解度或违反明确规则时才构成 finding（发现项）。

## 输出

按严重程度列出 finding，每项包含紧凑位置、触发场景、具体影响，以及现有测试或保护为何不能阻止。没有 finding 时明确说明，并指出未覆盖的测试、平台或行为风险。
